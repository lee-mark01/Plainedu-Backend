# 시세 데이터 전략 — 비용·신선도 검토와 단계별 계획

> 작성 2026-07-27 · 작성자: eun (리그/계좌평가 담당)
> 근거: 코드 실측 검증(2026-07-26 계좌평가 write-back E2E) + 코드 리딩. 인용 경로는 전부 현재 코드 기준.
> 목적: ① 현재 시세 파이프라인의 구조·비용·한계를 팀이 같은 그림으로 보기 ② 단기 수정/장기 결정 합의

## TL;DR

1. 가격 소스는 `chartService.getQuote` 하나로 잘 통합돼 있고(차트·체결·수익률·랭킹 전부 같은 값), 캐시 설계도 건강하다. **아키텍처 문제가 아니라 "전 종목 거래 가능 vs 실시간 데이터 8종목 + REST 800콜/일"이라는 범위-예산 불일치가 문제.**
2. 그 결과: WS 4종목(AAPL 등) 외 전 종목은 현재가·수익률이 **최대 5분에 한 번** 움직인다. "가격 보다가 타이밍에 매도"라는 핵심 루프가 대부분 종목에서 뭉개짐. 유저 ~100명 규모의 자유 탐색이면 REST 일 한도(800)도 초과.
3. 단기(무료 플랜 유지): **거래 가능 종목 화이트리스트(30~50개) + REST 호출 제한기 + 신선도 표시**로 공정하고 예측 가능하게 만든다.
4. 장기(월 ~12만원 플랜, API 610/분 + WS 500심볼): WS가 500종목이 되므로 화이트리스트 전체가 실시간이 됨. 현재 구조상 코드 변경 최소로 이행 가능. **결제 트리거 지표를 미리 합의해두자.**
5. "실시간 시세를 유저에게 유료 판매"는 **비추천** — 랭킹 리그에서 데이터 신선도를 팔면 pay-to-win이 되어 경쟁 공정성이 무너지고, 학생 대상 결제 인프라 비용이 플랜 비용을 초과한다.

## 1. 현재 구조 (사실 확인)

```
TwelveData WS (연결 1개, REALTIME_SYMBOLS ≤8 — 현재 AAPL, BTC/USD, EUR/USD, USD/KRW)
   └→ tickProcessor → Redis price:{symbol} (TTL 60s) → Socket.IO 브로드캐스트 (차트/헤더 실시간)
TwelveData REST time_series → Redis chart:{sym}:{interval} 캐시
   └→ TTL(장중): 5min봉 30s / 30min봉 60s / 1day 300s / 1week·1month 3600s · (장외) 전부 1800s

chartService.getQuote(symbol):  ① WS 틱 있으면 틱 가격  ② 없으면 일봉 마지막 종가
   └→ 소비자: 차트 헤더(/quote) · 시장가 체결(trading) · 수익률(/accounts/me) · 랭킹 배치 · 관심종목 · 포트폴리오
```

- 수익률 배치(`account.valuation.fetchPriceMap`)는 **WS 틱을 1순위로 mget** 후, 없는 심볼만 getQuote 폴백. "차트는 WS인데 정산은 REST" 같은 분리는 없음 — 소스는 하나다.
- 체결가와 화면 표시가가 같은 소스라 "보여준 가격 따로, 체결가 따로" 문제도 없음.
- 시세 실패 정책(D4)은 실측 검증 완료: 단건은 평단가+`price_stale`, 배치는 해당 계좌 skipped(DB·ZSET 직전 값 유지, updated_at 안 바뀜 확인).
- 서버가 주기적으로 하는 일은 WS 수신뿐이고 나머지는 전부 요청 시 pull + 캐시. 

## 2. 문제 정의

### P1. 실시간 경험이 8종목 한정 → 핵심 루프 손상
`Stocks` 테이블은 사실상 미국 전 종목(워런트 포함)이고 FK만 맞으면 뭐든 살 수 있다. 그러나 WS 없는 종목의 현재가는 "형성 중인 오늘 일봉의 close를 최대 300초에 한 번 새로 받는 값"이다. **유저가 화면을 보고 있어도 가격이 5분에 한 칸씩만 움직인다** → 매도 타이밍 훈련이라는 상품 가치가 대부분 종목에서 성립하지 않는다.
(참고: 무료 시세 15~20분 지연은 업계 표준이라 지연 자체는 문제가 아니다. **지연 사실을 화면에서 숨기는 것**이 문제 — §4-C 참조)

### P2. REST 예산 산수가 안 맞음 (무료: 800/일, 8/분)
- 비실시간 종목 1개를 장중(390분) 내내 5분 신선도로 유지 = 78콜/일 → **10종목이면 780콜, 하루 예산 끝.**
- 1D 차트(5분봉)는 TTL 30초라 상세페이지 열람이 사실상 매번 1크레딧. 과거 드래그(`before`)는 캐시를 안 타서 당길 때마다 1크레딧.
- 시나리오 실측 추정: 활성 유저 100명 × 상세 4회/일(1D+드래그) ≈ 800크레딧 — 이것만으로 한도 소진. 보유종목 30개 워밍 + 랭킹 1분 크론까지 돌면 **일 3,000+ 크레딧 vs 한도 800.**

### P3. 429 폭발이 "무작위 계좌 skip"으로 전이
`fetchPriceMap`은 캐시 미스 심볼을 `Promise.allSettled`로 동시 발사한다. 콜드 캐시(서버 재시작, 장 시작 직후)에 심볼 20개면 분당 8회 한도를 즉시 초과 → 초과분 429 → 그 종목 보유 계좌 전원이 그 사이클에서 skipped. **어떤 계좌의 랭킹이 멈출지 운이 결정한다.**

### P4. 일봉 캐시의 이중 소비자 (설계 냄새)
같은 `chart:{sym}:1day` 캐시를 ① 3M/1Y 차트(5분 묵어도 무해)와 ② 현재가·체결가·수익률(신선할수록 좋음)이 공유한다. 거래·정산용 가격의 신선도가 차트 캐시 TTL의 부산물로 결정되는 구조. (당장 고칠 건 아니고, 개선 시 분리 지점이라는 기록)

## 3. 선택지 비교

| | A. 무료 + 화이트리스트 (당장) | B. 유료 플랜 ~12만원/월 (트리거 도달 시) | C. 유저에게 실시간 유료 판매 |
|---|---|---|---|
| 내용 | 거래 가능 종목 30~50개 제한, 상위 8개 WS | API 610/분 + **WS 500심볼** | 비화이트리스트 실시간 = 결제 |
| 실시간 커버 | 8종목 (인기 종목 위주 재배치) | 화이트리스트 전체(≤500) 실시간 | 결제자만 |
| 비용 | 0원 | ~12만원/월 | PG·정산·환불 구축비 + 운영비 |
| 리그 공정성 | ✅ 전원 동일 데이터 | ✅ 전원 동일 데이터 | ❌ **pay-to-win — 랭킹 경쟁 전제 붕괴** |
| 비고 | 대부분의 교육용 모의투자가 채택하는 방식 | 현 구조상 이행 비용 낮음(§5) | 학생(미성년) 결제 전환율·법무 부담. **비추천** |

**권장: A → (지표 트리거) → B.** C는 채택하지 않는다.
B 이행 트리거(제안, 팀 합의 필요): DAU 50+ 지속 / 장중 429 에러 일 상시 발생 / 화이트리스트 확대 요구가 실제 유저에게서 나올 때.

플랜 스펙 참고: "Credits: 610 API + 500 WS, 70+ markets, Real-time EU …" — API 610은 분당 크레딧, WS 500은 구독 심볼 수로 해석됨. **결제 전 요금 페이지에서 분당/일 한도 체계 재확인 필요** (무료의 800/일 같은 일 한도가 유료에 있는지).

## 5. 왜 지금 구조를 갈아엎지 않는가

`getQuote` 단일 진입점 + 캐시 계층 + D4 실패 정책은 그대로 두고 위 액션만 하면 된다. 플랜을 올리면 **같은 코드가 자동으로 500종목 실시간이 된다** (fetchPriceMap의 1순위가 WS 틱이므로). 데이터 제공사를 바꾸더라도 교체 지점이 `twelvedata.client` + `wsUpstream` 두 파일로 고립돼 있다. 즉, 지금의 레이어링이 미래 결정을 싸게 만들어 주는 상태라 재설계는 불필요하다.
