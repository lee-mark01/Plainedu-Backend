# 시세 구독 아키텍처 설계 — 태그 기반 WS 슬롯 관리

---

## 1. 배경

현재 시세는 Twelve Data에서 WebSocket + REST로 받는다. 유료 플랜 전환을 앞두고 쿼터 안에서 동작하도록 구독 정책을 정한다.

**플랜 쿼터**

| 자원 | 한도 | 성격 |
| --- | --- | --- |
| REST | 610 credits/min, **6,100 credits/day** | 일일 한도가 진짜 병목 |
| WebSocket | **500 동시 구독 슬롯** | 구독/해제 횟수 제한 없음 |

DB에 적재된 미국 종목은 수천 개라 전부 실시간 구독은 불가능하다.

### 1-1. 가장 먼저 알아야 할 것: 분당이 아니라 일당이다

미국 정규장은 390분이다. 6,100 ÷ 390 = **분당 평균 15.6 credits**가 실제 예산이다. 610/min은 10분이면 일일 한도를 태우는 버스트 상한일 뿐이다.

> **이 플랜으로 사는 것은 REST 처리량이 아니라 WS 슬롯 500개다.**
> 따라서 자주 필요한 가격은 최대한 WS로 밀고, REST는 차트 히스토리·전일종가·미구독 종목 단발 조회만 남긴다.

WS 틱은 크레딧을 소모하지 않는다. 슬롯만 점유한다.

## 2. 현재 구조의 실제 비용 (수정 전)

측정이 아니라 코드에서 역산한 값이다.

### 문제 A — 전일종가 갱신이 최대 비용 🔴

`tickProcessor.js:13`의 `PREV_CLOSE_REFRESH_MS = 5분`. 5분마다 `chartService.getPrevClose()` → `getDailyCandles()` → 1day 캐시 조회. 그런데 `rangeMap.js:28`의 1day 장중 TTL도 300초라 **두 캐시가 같이 만료되면서 5분마다 REST 1크레딧**이 나간다.

```
심볼당: 390분 ÷ 5분 = 78 credits/day
```

| 구독 종목 수 | 전일종가 비용 | 일일 한도 대비 |
| --- | --- | --- |
| 50 | 3,900 | **64%** |
| 100 | 7,800 | **128% (초과)** |
| 200 | 15,600 | **256% (초과)** |

**전일종가는 ET 거래일 동안 절대 변하지 않는 상수다.** 5분마다 갱신할 이유가 없다.

### 문제 B — 랭킹 스케줄러가 이 비용을 매분 유발

`rankingScheduler.js:5` 주석대로 매분 recompute가 보유 종목 일봉 캐시를 리필한다. 캐시 워밍 의도는 맞지만, 위 5분 TTL과 맞물려 보유 종목 수만큼 문제 A가 곱해진다.

### 문제 C — 크레딧 사용량을 아무도 모른다

일일 소비량을 세는 곳이 없다. 6,100을 언제 넘는지, 넘었는지조차 알 수 없다. 한도를 소진하면 **남은 하루 전체가 429**인데 모든 요청이 계속 API를 때린다.

## 3. 설계: 태그 기반 구독

### 3-1. 핵심 아이디어

WS 구독은 **하나의 집합**이고, 각 심볼에 "살아있어야 할 이유"를 태그로 붙인다. 태그가 0개가 되면 해제한다.

```
AAPL   {core, held, view:x7f}   ← 이유 3개, 슬롯은 1개
GME    {held}                    ← 마지막 보유자가 팔면 해제
PLTR   {view:a3b}                ← 유저 이탈 후 해제
KO     {core}                    ← 아무도 안 봐도 유지
```

**구간을 나누지 않는다.** "코어 200 / 보유 300" 같은 고정 분할은 성립하지 않는다. 코어 종목이 보유되어도 슬롯을 추가로 먹지 않기 때문이다 — 겹칠수록 총 슬롯이 줄어든다.

| 상황 | 코어 밖 보유 | 총 슬롯 |
| --- | --- | --- |
| 보유 80종목 중 40개가 코어와 겹침 | 40 | 90 |
| 보유 80종목이 전부 코어 안 | 0 | 50 |
| 보유 80종목이 전부 코어 밖 | 80 | 130 |

### 3-2. 태그 3종

| 태그 | 소스 | 존재 이유 | 규모 |
| --- | --- | --- | --- |
| `core` | 설정 배열 | **리스트 페이지**가 소비자 — 항상 전부 필요 | 50 (→ 확장) |
| `held` | `holdings` 테이블 | **랭킹 배치**가 1분마다 가격을 요구 | 코어 밖 수십 |
| `view:{socketId}` | Socket.IO | 상세페이지 실시간 | 동시 조회 수 |

**관심종목(watchlist)에는 태그를 붙이지 않는다.** 판별 기준은 "누가 갱신을 요구하는가"다.

|  | 갱신 트리거 | 지연 허용 | 결론 |
| --- | --- | --- | --- |
| 관심종목 | 유저가 탭을 열 때 | 수 분 OK | REST |
| 보유종목 | **서버가 1분마다** (랭킹) | 안 됨 | WS |

관심종목은 유저가 안 보면 아무도 조회하지 않는다. 보유종목은 유저가 자든 말든 서버가 매분 계산한다. 그리고 `chart.service.js:132-152`의 `getQuote`가 이미 "구독 중이면 WS 틱, 아니면 일봉 종가"로 동작하므로 **관심종목은 추가 코드가 필요 없다.**

### 3-3. 해제 유예는 태그가 아니라 "해제 판정"에 건다

태그별 유예 정책을 따로 만들지 않는다. 태그 제거는 항상 즉시이고, 유예는 집합이 빈 다음 한 번만 건다.

```jsx
const remove = (symbol, reason) => {
  const tags = subs.get(symbol);
  if (!tags?.delete(reason)) return;
  if (tags.size > 0) return;                 // 다른 이유가 남음 → 아무것도 안 함
  pending.set(symbol, setTimeout(() => {     // 집합이 빔 → 해제 예약
    pending.delete(symbol);
    if (subs.get(symbol)?.size === 0) {      // 5분 뒤 재확인 (그 사이 붙었으면 취소)
      subs.delete(symbol);
      upstream.unsubscribe(symbol);
    }
  }, RELEASE_GRACE_MS));
};

const add = (symbol, reason) => {
  clearTimeout(pending.get(symbol));         // 예약된 해제 취소
  pending.delete(symbol);
  // ... 태그 추가, 신규 심볼이면 upstream.subscribe
};
```

유예 로직이 한 군데에만 있고 세 태그가 전부 혜택을 본다.

**결과: 전량 매도 후 실제 해제까지 두 겹의 지연**

```
전량 매도 ──(최대 60초: 다음 동기화 스냅샷)──▶ held 태그 제거
         ──(5분: 해제 유예)──▶ 실제 unsubscribe
                                        총 5~6분
```

단타로 팔았다 다시 사면 그 안에 들어와 구독이 끊기지 않는다. 슬롯이 남으므로 이 5분은 공짜다.

### 3-4. 슬롯 정책

- **축출(LRU/LFU) 로직 없음.** 500이 차면 Twelve Data가 subscribe를 거절하고, `wsUpstream.js:42`가 `fails`로 받고, `price:{symbol}`이 없으니 `getQuote`가 일봉 종가로 폴백한다. **전 경로가 이미 구현되어 있다.** 장애가 아니라 지연으로 내려앉을 뿐이다.
- **500이 차려면 코어 밖 보유/조회 종목이 450개**여야 한다. 초기 규모에서는 오지 않는다.
- 그 시점이 오면 선택지는 런타임 LRU가 아니라 **코어 배열 축소** 또는 **플랜 상향**이다. 런타임 LRU는 "지금 어느 종목이 실시간인지"를 매 순간 바꿔서 재현 불가능한 버그를 만든다.

### 3-5. 코어 목록은 수요 데이터로 재조정

시총 상위 50은 **데이터가 없는 첫 몇 주의 대용품**이다. 수요 카운터를 쌓아 실측으로 교체한다.

```jsx
// getQuote() 진입부 + wsGateway subscribe 핸들러, 각각 한 줄
redis.zincrby(`demand:${yyyymm}`, 1, symbol);
```

조정할 때 `ZREVRANGE`로 상위 N을 뽑으면 끝이다. 축출 로직도 타임스탬프 추적도 필요 없다. 월 단위 키라 오래된 인기가 영원히 남지도 않는다.

이 카운터 하나가 세 질문에 동시에 답한다.

| 질문 | 답 |
| --- | --- |
| 코어를 50 → 200으로 늘릴까? | 상위 200에 실제 수요가 있나 |
| 코어에서 뭘 뺄까? | 하위 랭크 |
| 계속 시총순으로 갈까? | **아니오** — 학생들이 보는 종목은 시총순과 다를 것 |

## 4. 태그별 운영 정책

### `core` — 정적

| 항목 | 정책 |
| --- | --- |
| 붙음 | 서버 시작 시 배열 전체를 1개 메시지로 배치 subscribe |
| 떨어짐 | 없음 |
| 변경 | 배열 상수 수정 후 재배포 (월 1회 수준) |
| 실패 | `fails`에 코어 심볼이 있으면 **error 레벨** — 상폐/오타/플랜 미지원이므로 사람이 봐야 함 |

현재 `fails`는 `wsUpstream.js:43`에서 일괄 `console.warn`이다. 코어 심볼 거절은 정상 상황이 아니므로 로그 레벨을 분리한다.

> **런타임 코어 변경 API는 만들지 않는다.** 월 1회 배열 수정이면 재배포로 충분하고, API를 만들면 인증·권한·감사로그가 줄줄이 따라온다.

### `held` — 1분 주기 스냅샷 동기화

| 항목 | 정책 |
| --- | --- |
| 소스 | `SELECT DISTINCT stock_code FROM holdings WHERE quantity > 0` |
| 주기 | 1분 — `rankingScheduler`에 편승 |
| 위치 | **`isMarketOpen()` 가드보다 앞** ⚠️ |
| 방식 | 스냅샷 diff — 결과에 없으면 태그 제거, 있으면 추가 |
| **DB 실패** | **no-op. 태그를 절대 건드리지 않는다** |

**⚠️ 위치가 중요하다.** `rankingScheduler.js:28`의 `tick()`은 `if (!isMarketOpen()) return`으로 시작해서 장 마감 중에는 아예 돌지 않는다. `tick()` 안에 동기화를 넣으면 장외 매수분이 개장 후에야 반영되어 **개장 직후 공백**이 생긴다. `running` 가드와도 무관한 가벼운 작업이므로 별도 함수로 분리해 가드 밖에서 호출한다.

**DB 실패 시 no-op이 제일 중요하다.** 쿼리가 실패했는데 빈 배열로 sync하면 **전 보유종목 구독이 한 번에 해제된다.** try/catch로 감싸고 실패 시 return. 다음 주기가 복구한다.

`holdings.stock_code` 인덱스를 확인해야 한다. 1분마다 DISTINCT 풀스캔이 도는 건 계좌가 늘면 부담이다.

**매수 직후 최대 1분 공백은 실제로 생기지 않는다.** 유저가 상세페이지에서 사므로 `view:{sid}` 태그가 이미 붙어 있고, `view` 유예 5분 > 동기화 주기 1분이라 페이지를 바로 나가도 held가 붙기 전에 구독이 끊기지 않는다. 이 부등식이 구조적으로 공백을 막는다.

### `view:{socketId}` — 추가는 즉시, 제거는 즉시 + 주기 안전망

| 항목 | 정책 |
| --- | --- |
| 붙음 | Socket.IO `subscribe` 이벤트 — **즉시** |
| 떨어짐 | `unsubscribe` / `disconnect` — 즉시 |
| 안전망 | 1분 주기에 `io.sockets.adapter.rooms` 스캔 → 빈 room의 잔여 태그 정리 |

비대칭인 이유: 추가가 늦으면 유저가 "왜 안 움직이지?" 하고, 제거가 늦으면 슬롯만 조금 더 쓴다.

**⚠️ `disconnect` 핸들러가 현재 없다.** `wsGateway.js:16-33`에 `subscribe`/`unsubscribe`만 있어서, 브라우저 탭을 닫으면 태그가 영원히 남는다 — 슬롯 누수 직행이다.

`socketId`를 태그에 넣는 이유는 같은 종목을 10명이 보면 태그가 10개 달려야 하기 때문이다. 1명이 나가도 9개가 남아 구독이 유지된다.

## 5. 상태를 어디에 저장하나

| 데이터 | 위치 | 이유 |
| --- | --- | --- |
| 구독 집합 `subs` | **프로세스 메모리** | 재시작 시 전부 자동 복구되므로 영속화 불필요 |
| 코어 목록 | **설정 파일 (코드)** | 배포 단위로 바뀌는 게 맞음. DB면 마이그레이션+어드민이 따라옴 |
| 보유 종목 | **DB** (`holdings`) | 이미 진실원천. 별도 저장 안 함 |
| 수요 카운터 | **Redis ZSET** | 조회마다 쓰기가 발생 — DB write는 비쌈. 없어져도 되는 통계 |
| 현재가 | **Redis** (`price:{symbol}`) | 기존 그대로 |
| 일일 크레딧 사용량 | **Redis** (`credits:{YYYY-MM-DD}`) | 신규. 아래 §7 |

**구독 집합을 DB/Redis에 영속화하지 않는다.** 서버가 재시작하면:

- `core` → 배열에서 즉시 복구
- `held` → 첫 동기화(최대 1분)에서 복구
- `view` → 프론트가 재연결하며 다시 subscribe

세 경로 모두 자동이다. 영속화하면 "저장된 상태와 실제 구독의 불일치"라는 새 문제만 생긴다.

## 6. REST 비용 재조정 (가장 큰 절약)

### 6-1. 전일종가를 하루 1회로 🔴 최우선

`prevCloseCache`의 만료 기준을 경과 시간이 아니라 **ET 거래일**로 바꾼다. `marketHours.js`의 `getEtDateString()`이 이미 있다.

```
변경 전: 심볼당 78 credits/day
변경 후: 심볼당  1 credits/day
```

| 구독 종목 수 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 50 | 3,900 | 50 |
| 200 | 15,600 | 200 |

**약 5줄 변경으로 예산의 64%가 회수된다.** 이것만으로 코어 200까지 열린다.

### 6-2. 1day 장중 TTL 상향

`rangeMap.js:27`의 `'1day': 300` → **900** (15분) 검토.

이 캐시는 §6-1 이후 차트(3M/1Y)와 미구독 종목 `getQuote`에만 쓰인다. 구독 종목의 현재가는 WS 틱이 담당하므로 영향이 없고, 미구독 종목은 어차피 지연 시세다. 크레딧 5배 절약, 미구독 종목 지연 5분 → 15분.

**팀 결정 필요:** 검색 결과에 뜨는 종목의 가격이 최대 15분 지연되는 것이 허용 가능한가?

### 6-3. `price:{symbol}` TTL 상향

`tickProcessor.js:9`의 60초 → **180초** 검토.

장중이라도 60초간 체결이 없으면 만료되어 REST로 폴백한다. 코어 대형주는 문제없지만 코어 밖 저유동성 보유종목에서 발생한다. 랭킹이 1분 주기이므로 3주기까지 커버된다. 신선도는 `account.valuation.js:29`의 `priced_at`으로 이미 프론트에 전달되고 있다.

### 6-4. 수정 후 예상 예산

| 항목 | credits/day |
| --- | --- |
| 전일종가 (코어 50 + 보유) | ~100 |
| 차트 히스토리 (조회 시에만) | 수백 |
| 미구독 종목 `getQuote` | 수백 |
| **합계** | **~1,000 / 6,100** |

여유가 충분해 코어를 200까지 늘릴 수 있다.

## 7. 관측과 방어

### 7-1. 반드시 넣어야 할 것

**① 소켓당 view 제한 + 심볼 검증** 🔴 보안

현재 게이트웨이에 인증이 없다. `allowedSymbols` Set이 사라지면 **아무나 접속해 임의 심볼 수천 개를 subscribe 할 수 있고, 500슬롯이 포화되어 코어와 보유종목이 전부 REST 폴백으로 밀린다.** 실제 취약점이다.

```jsx
socket.on('subscribe', async ({ symbol }) => {
  if (viewCount(socket.id) >= MAX_VIEWS_PER_SOCKET) return reject('구독 한도 초과');
  if (!(await stockRepository.findByCode(symbol))) return reject('없는 종목');
  ...
});
```

상세페이지는 한 번에 하나이므로 소켓당 3개면 넉넉하다. 3개 제한이면 500슬롯을 채우는 데 소켓 167개가 필요하고 그건 정상 트래픽 규모다. 심볼 검증이 없으면 쓰레기 문자열이 그대로 Twelve Data로 나간다.

**② 재연결 시 현재 구독 집합 재전송**

`wsUpstream.js:62`가 클로저에 캡처된 고정 `symbols`를 다시 보낸다. 동적 집합이 되면 재연결마다 **초기 목록으로 되돌아가 그동안 붙은 held/view가 전부 날아간다.** `createUpstream({ getSymbols: () => subscriptions.list() })`로 바꾼다.

**③ 구독 변경 배치**

1분 동기화에서 held가 여러 개 바뀌면 subscribe 메시지 하나로 묶는다. Twelve Data가 콤마 구분 다중 심볼을 받으므로 기존 형식 그대로 쓴다.

**④ 일일 크레딧 카운터**

`twelvedata.client.js`의 요청 지점에서 `INCR credits:{YYYY-MM-DD}`. 없으면 예산을 얼마나 쓰는지 아무도 모른다. 서킷 브레이커는 실제로 한도 근처에 가는 게 보이면 그때 추가한다.

### 7-2. 1분 주기 관측 로그

기존 스케줄러 로그에 한 줄 추가한다.

```
[marketData] 슬롯 87/500 (core 50 · held 31 · view 12 · 유예중 3) · credits 412/6100
```

슬롯 400 초과 또는 크레딧 5,000 초과 시 경고 레벨로 올린다.

### 7-3. 테스트

`subscriptions.js`의 태그 add/remove/유예 로직은 분기가 있으므로 테스트를 남긴다. `npm test`(`node --test`)가 이미 있고 `tests/`에 6개 파일이 있다.

최소 케이스: 태그 2개 중 1개 제거 시 구독 유지 · 마지막 태그 제거 시 유예 후 해제 · 유예 중 재추가 시 해제 취소 · DB 실패 시 held 태그 불변.

`rankingScheduler.js:2-4` 주석에 이미 경고가 있다. WS도 같은 문제를 갖는다 — 서버를 2대 띄우면 각자 WS 연결을 잡고 각자 구독해서 **슬롯을 2배 먹는다.**

## 11. 팀 확인이 필요한 사항

1. **1day 장중 TTL 15분** — 검색 결과 종목 가격이 최대 15분 지연되는 것이 허용 가능한가? (§6-2)
2. **틱 처리량 미측정** — 코어 50 장중 초당 틱 수를 모른다. `tickProcessor.js:47-78`이 틱마다 Redis SET + `getPrevClose` await + 전 priceListener 순차 await를 돈다. 3종목일 땐 무해하지만 50종목이면 17배다. 특히 trading이 `priceListener`로 지정가 체결 검사를 붙이면 그것도 틱마다 돈다. `spikes/twelvedata-ws-test/` 하네스로 **미국장 시간(한국시간 23:30~)** 에 30분 측정하면 코어 크기 상한과 틱 병합 필요 여부가 동시에 정해진다. 필요하면 해법은 심볼당 마지막 틱만 200ms 주기로 flush하는 병합이다.
3. **한국 낮 = 미국장 마감** — 미국 정규장은 한국시간 23:30~06:00이다. **유저가 앱을 켜는 대부분의 시간에는 틱이 0건**이고 모든 화면이 정지 상태다. 실시간이 핵심 가치라면 그 가치가 실현되는 창이 좁다는 것을 알고 가야 한다. 현재 기본 심볼에 `BTC/USD`, `EUR/USD`가 들어 있는데, 크립토 2~3개를 코어에 넣으면 낮에도 움직이는 화면이 생긴다. **제품 결정 사항.**
4. **프론트 계약 변경** — `subscribe-error`의 의미가 "실시간 미제공 종목"에서 "없는 종목 / 구독 한도 초과"로 바뀐다. 슬롯 포화로 구독을 못 받았을 때 프론트에 무엇을 보낼지 합의가 필요하다. `account.valuation.js:29`에 이미 `price_source` / `priced_at` 신선도 배지 재료가 있으므로 같은 계약을 상세페이지에도 쓰면 일관된다.
5. **`docs/market-data-strategy.md` 부재** — `account.valuation.js:15`와 `rankingScheduler.js:6`이 이 문서를 참조하는데 `docs/`에 없다. 이 문서가 그 자리를 대신할지, 별도로 복원할지 정해야 한다.
