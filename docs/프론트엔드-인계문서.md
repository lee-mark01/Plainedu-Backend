## 2. 인증 시스템

**소셜 로그인만 있습니다** (카카오 / 네이버 / 구글). 자체 회원가입·비밀번호 없음.

```
프론트에서 OAuth 인가코드(code) 획득
   ↓
POST /api/auth/{kakao|naver|google}  { code }   ← 네이버는 state도 함께
   ↓
{ accessToken, refreshToken, user }
```

| 항목 | 값 |
|---|---|
| 액세스 토큰 | **15분** — 요청 헤더에 `Authorization: Bearer {accessToken}` |
| 리프레시 토큰 | **7일**(미사용 시 만료) / **90일**(절대 만료) |
| 갱신 | `POST /api/auth/refresh` `{ refreshToken }` → 새 토큰 쌍 |

### 프론트가 꼭 알아야 할 3가지

1. **신규 가입 여부는 응답 body가 아니라 HTTP 상태코드로 옵니다.**
   `201` = 방금 가입한 신규 유저 → 온보딩으로, `200` = 기존 유저 → 홈으로.

2. **리프레시 토큰은 1회용입니다(rotation).** 갱신하면 이전 토큰은 즉시 폐기되니, 응답으로 받은 **새 refreshToken으로 반드시 교체 저장**하세요.
   이미 쓴 토큰을 다시 보내면 탈취로 간주해 **해당 기기의 토큰 계보를 전부 삭제**하고 `401 TOKEN_REUSE_DETECTED`를 던집니다 → 강제 재로그인.
   ⚠️ 갱신 요청이 동시에 여러 개 나가면(401 뜬 요청들이 한꺼번에 재시도) 이게 그대로 터집니다. **갱신은 한 번만 돌고 나머지는 대기시키는 큐**를 꼭 두세요.

3. **401 코드별로 분기하세요.**

| code | 의미 | 처리 |
|---|---|---|
| `REFRESH_TOKEN_EXPIRED` | 리프레시 만료 | 재로그인 |
| `REFRESH_TOKEN_INVALID` | 없는/잘못된 토큰 | 재로그인 |
| `TOKEN_REUSE_DETECTED` | 재사용 감지 | 저장된 토큰 전부 삭제 후 재로그인 |
| `PROVIDER_CONFLICT` (409) | 같은 이메일이 다른 소셜로 이미 가입 | "카카오로 로그인해주세요" 안내 (message에 제공자명 들어있음) |

## 3. 온보딩 플로우

로그인 직후(`201`) 태워야 하는 순서입니다. **개인 모드는 ①만으로 전부 사용 가능**하고, ②③은 팀 모드를 쓸 때만 필요합니다.

```
① 로그인            POST /api/auth/kakao          → 201이면 신규
                    (개인 가상계좌는 서버가 자동 생성 — 프론트 할 일 없음)
   ↓
② 학교 선택         GET   /api/schools?keyword=연세   ← 검색
                    PATCH /api/users/me { school_id }  ← 선택        ⭐신규
   ↓
③ 대학 이메일 인증   POST /api/auth/email/send   { email }
                    POST /api/auth/email/verify { email, code }
   ↓
④ 팀 생성 / 가입     POST /api/teams ...        ← ②③ 둘 다 있어야 통과
```

- 현재 진행 상태는 `GET /api/users/me`의 `school: { id, name, is_verified }`로 판단하세요 (미선택이면 `null`).
- ②③을 건너뛴 유저가 ④를 호출하면 **403**입니다. 팀 탭 진입 시점에 미리 막아주는 게 좋습니다.
- 학교를 **다시** 고르면 인증이 자동으로 풀립니다 → ③을 다시 태워야 합니다.

## 5. 공통 규격

전문은 [api-conventions.md](api-conventions.md). 요약하면:

**성공** — `{ "success": true, "data": ... }` · **실패** — `{ "success": false, "message": "...", "code": "..." }`
(`code`는 없을 수도 있습니다. 분기는 `code` 우선, 없으면 status로.)

| status | 의미 |
|---|---|
| 400 | 입력값 오류 |
| 401 | 미인증·토큰 만료 |
| 403 | 권한 없음 / **선행조건 미충족**(학교 인증 등) |
| 404 | 없음 |
| 409 | 상태 충돌 (중복 등록, 이미 투표) |
| 429 | **요청 한도 초과** — `code: RATE_LIMITED`, `Retry-After` 헤더(초)만큼 대기 |
| 500 | 서버 오류 — message는 고정 문구, 파싱하지 마세요 |

- 시간은 전부 **UTC ISO 8601**(`"2026-07-19T02:30:00.000Z"`). 표시할 때 KST 변환 필요.
- **페이지네이션은 두 방식이 섞여 있으니 주의**하세요:
  - 페이지 번호형 — `?page=&limit=` → `pagination: { page, limit, total }` (trading 주문내역 등)
  - 무한스크롤형 — `?cursor=&limit=` → `hasNext` (community 피드)

## 6. 이번 릴리스 변경사항

> ⚠️ **아직 서버에 배포 전입니다** (2026-08-14 확인). 지금 `school_id`를 보내면 400이 납니다.
> Swagger에서 `PATCH /api/users/me`에 `school_id`가 보이면 반영된 겁니다.

### 6-1. 학교 선택 지원 (PM-04) ⭐

`PATCH /api/users/me`가 `school_id`를 받습니다. 이걸로 온보딩 ②단계가 열렸습니다.

**Request** — 둘 다 선택 항목이고 **최소 1개**는 보내야 합니다:

```json
{ "nickname": "새닉네임", "school_id": 42 }
```

| 필드 | 타입 | 비고 |
|---|---|---|
| `nickname` | string, 1~50자 | 기존과 동일 |
| `school_id` | integer ≥ 1 | `GET /api/schools` 결과의 `id` 그대로 |

**에러**:

| status | 상황 | 처리 |
|---|---|---|
| 400 | 빈 body / 형식 오류 | `message` 노출 |
| 404 | 없는 `school_id` | "존재하지 않는 학교입니다." |
| 409 | **팀 소속 중 학교 변경** | 팀에 속해 있으면 학교 변경 UI를 아예 막는 걸 권장 (`GET /api/users/me`의 `team !== null`) |

**부수 효과** — 학교를 바꾸면 ① `school_is_verified`가 꺼지고(재인증 필요) ② 개인계좌의 리그 그룹(고교/대학)이 새 학교 기준으로 재계산됩니다. 랭킹 화면에서 다른 그룹으로 보이는 게 정상입니다.
같은 학교를 다시 보내면 아무 일도 안 일어납니다(인증 안 풀림). `position`은 여전히 이 API로 변경 불가.

### 6-2. 이메일 인증 rate limit 주의

- 발송은 **1시간에 3회**뿐입니다. 429 뜨면 `Retry-After`만큼 대기 — **재발송 버튼에 쿨다운을 걸어주세요.**
- 코드 TTL 5분, 확인은 5분에 10회. 만료 시 `CODE_EXPIRED`(재발송 유도), 불일치 시 `CODE_MISMATCH`.
- 대학 도메인이 아니면 `INVALID_UNIVERSITY_EMAIL`.

### 6-3. 500 응답 고정

500은 이제 항상 `{ "success": false, "message": "서버 내부 오류가 발생했습니다." }`입니다(`code` 없음).
이전엔 DB 에러 원문이 새어나가는 경우가 있었습니다. **500의 message를 파싱하거나 분기하던 코드가 있으면 제거하세요.**

| 지난 시즌 조회 / 시즌 전환 | 미구현 |
